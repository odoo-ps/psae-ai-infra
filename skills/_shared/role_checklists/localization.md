# Localization

*Calibrated against Odoo 19.0. Re-review on each major version bump.*

## Goal
If the addon will be deployed across languages, currencies, companies, or regions, surface the i18n / l10n decisions early.

## Key Questions to Ask the User
- Will this addon be deployed in **multiple languages**? Which?
- Are there **monetary fields**? Should they be expressed in the company's currency, the partner's currency, or a fixed currency?
- Is the deployment **multi-company**? Should records be company-scoped?
- Are dates / numbers / addresses formatted **per-locale** (date format, decimal separator, postal code shape)?
- Do views need to support **RTL languages** (Arabic, Hebrew)?
- Does the deployment target a **country pack** (`l10n_<cc>`)? If yes, which? The country pack defines the chart of accounts, taxes, fiscal positions, and (often) e-invoicing integration. A custom addon that touches accounting / invoicing must coexist with the country pack, not override it.
- Is **e-invoicing** required for this region? Saudi Arabia's ZATCA, Italy's SdI/FatturaPA, India's GST e-invoicing, EU's Peppol — each has dedicated Odoo Enterprise modules; custom addons that touch invoice flow must respect them.

## Mechanisms / Tools
- **Translatable strings** in Python: wrap user-facing text in `_()`:
  ```python
  from odoo import _
  raise UserError(_("Cannot delete a confirmed record."))
  ```
- **Translatable strings** in views: any `string=`, `help=`, `placeholder=` attribute is auto-translated. Field labels too.
- **`translate=True` on `Char` / `Text` fields** when the field's value itself should be translatable per language (e.g. product name).
- **Translation extraction**: `<addon>/i18n/<addon>.pot` is the template; `<addon>/i18n/<lang>.po` per language. Generated by `odoo-bin -c <conf> -d <db> --i18n-export=<file> --modules=<addon>` then translated.
- **Currency**: every monetary field should pair with a `currency_id` field via `currency_field=`:
  ```python
  amount = fields.Monetary(currency_field="currency_id")
  currency_id = fields.Many2one("res.currency", default=lambda self: self.env.company.currency_id)
  ```
- **Multi-company**: every model that holds company-scoped data needs `company_id = fields.Many2one("res.company", default=lambda self: self.env.company)` and a record rule scoping to it. See `security.md`.
- **RTL**: avoid hardcoding `text-align: left` / `padding-left` in custom CSS. Use logical properties (`text-align: start`, `padding-inline-start`) so RTL layouts mirror correctly.
- **Address formatting**: never hand-format `f"{street}, {city} {zip}"`. Use `partner._display_address()` or render with `country_id.address_format` so each country's expected layout (postal code position, region inclusion, salutation slot) is honoured.
- **Locale-aware sort discipline**: a model with `_order = "name"` where `name` is `translate=True` will sort by *the en_US value* even when the user's locale is `fr_FR`. If sort order matters (most lists), either don't translate the sort field, or use a separate `sort_name` Char that holds a normalized form, or accept the en_US sort and note it.
- **`res.partner.lang`** drives outgoing mail / report language per customer. Default fall-through: partner's lang → user's lang → company default. If your addon sends mail or renders reports, name which lang context you're rendering in (`with_context(lang=partner.lang or self.env.user.lang)`) and verify against a multi-lingual demo DB.
- **Country pack (`l10n_<cc>`) modules** ship the localization-specific chart of accounts, taxes, fiscal positions, and (often) e-invoicing flow. They install via the **Settings → Companies → Fiscal Localization** picker on first setup, NOT automatic. Adding accounting / tax behaviour without coordinating with the relevant `l10n_<cc>` is how you build duplicate or conflicting tax configurations.
- **E-invoicing per region** — ZATCA (Saudi Arabia), SdI / FatturaPA (Italy), GST e-invoice (India), Peppol (EU cross-border) all have dedicated Odoo Enterprise modules (`l10n_sa_edi`, `l10n_it_edi`, `l10n_in_edi`, `account_edi_ubl_cii`). A custom addon that touches the invoice posting flow must respect them — extend, don't replace.
- **`raise UserError("...")` without `_()`** — error message stays English even when the rest of the UI is translated.
- **Hardcoded date format `"%Y-%m-%d"`** in a user-visible context — locale displays differently. Use Odoo's `format_date` / `format_datetime` helpers.
- **`Float` field for money** — wrong; use `Monetary`. `Float` doesn't track currency, doesn't render with the right symbol/precision.
- **Multi-company model without `company_id`** — record rule can't filter; cross-company data leaks (also a security issue).
- **Forgetting to update the `.pot` file** when adding new translatable strings — translations go stale silently.
- **Hand-formatted addresses** — `f"{street}, {city} {zip}, {country}"` ignores country-specific layout (postcode-before-city in UK; postcode-after-state in US; salutation prefix in JP). Use `partner._display_address()` or `country_id.address_format`.
- **`_order` on a translatable field** — list sorts by en_US value silently regardless of user locale. If sort matters, use a non-translated sort field.

## Production-readiness criteria
- [ ] All user-facing Python strings wrapped in `_()`.
- [ ] Monetary fields use `Monetary` with explicit `currency_field`.
- [ ] Multi-company models have `company_id` + record rule.
- [ ] If translations targeted: `.pot` and at least one `.po` file present under `i18n/`.
- [ ] Custom CSS uses logical properties for RTL safety.
- [ ] Address-rendering uses `partner._display_address()` or `country_id.address_format`, never hand-formatted.
- [ ] `_order` does not sort by a `translate=True` field (or the en_US sort is explicitly accepted with a note).
- [ ] `translate=True` set on Char/Text fields whose value (not just label) varies per language — never on technical identifiers, codes, or references.

## Required artifacts (the plan must contain these)

1. **Locale targeting statement** — list the locales the addon is expected to run in (e.g. `en_US, fr_FR, ar_AE`) OR explicitly note "English-only deployment, no i18n work needed".
2. **Currency model** — for every Monetary field, name its `currency_field` and the source of that currency (company / partner / fixed). Empty list is a valid answer if no monetary fields.
3. **Multi-company decision per new model** — for every new model, declare "company-scoped (`company_id` + record rule)" or "company-agnostic (no `company_id`)". The decision affects ACL and security review.
4. **RTL surface inventory** — for every new view, declare RTL-safe (uses logical properties; no hardcoded `left`/`right` in custom CSS) or list the specific layout that needs manual RTL adaptation.
5. **Translatable-content inventory** — list every `translate=True` field and every user-facing string the addon adds. Empty list is a valid answer.
6. **Country-pack coexistence statement** — if the addon touches accounting, taxes, or invoicing, declare which `l10n_<cc>` modules it expects to coexist with and how it avoids duplicating their COA / tax configuration. "N/A — addon doesn't touch accounting/invoicing" is a valid answer.
7. **E-invoicing impact statement** — if the addon touches invoice posting / transmission flow, name the regional EDI module(s) it must respect (ZATCA / SdI / Peppol / GST) and how the addon extends rather than replaces them. Empty if the addon doesn't touch invoicing.
